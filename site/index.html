Five steps, each one checkable

1

Understand

A language model reads the request and labels the intent.

2

Look up

The code reads the real charges of the session account. The model sees no customer id.

3

Decide

The policy engine, in code, allows, refuses or hands off.

4

Verify

The code checks that the case exists before it says so.

5

Hand off

For fraud or a high amount, an advisor gets the verified facts.

Four cases to try

The customer replies in es-MX, es-CO, es-AR or pt-BR. The data behind the demo is synthetic and the Gold store is a labelled mock.

Normal case

One charge, one confirmation, one verified case number.

Ambiguous case

Several equal purchases. The system asks which one before it acts.

High amount

The system does not act alone. It hands off with the verified facts.

Not me

The system does not decide on fraud. It hands off to an advisor.

Limits and roadmap

Limits

  • Data: synthetic, in Spanish only, for three countries. The Portuguese cases are model-written.
  • Ceiling: the policy lets 16 of 56 simulated cases resolve (Simulation). The system resolves all of them and no other.
  • Mocks: the Gold store, login and session, the advisor, the case store and the policy values. Each keeps the production contract. Mocks.
  • Translations: the Spanish and Portuguese pages are model-written translations of the English pages. No native speaker reviewed them.
  • Numbers: none is a production measurement.

Roadmap: not built

  • Customer 360: the balance has no usable as-of date.
  • Charge investigation: it needs real bank data.
  • Feedback dataset: the outcomes of advisor handoffs.
  • Spending assistant: it needs balances and history.
  • Policy retrieval: it needs the policy documents of the bank.
  • Handoff routing: by language and specialty.

Each item has its evidence in the README roadmap.
