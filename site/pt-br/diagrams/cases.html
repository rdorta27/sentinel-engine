Três casos, um mapa de decisão

Os mesmos passos rodam todas as vezes. O código decide para onde o turno vai. Selecione um caso para iluminar sua rota.

Caso normal

Uma conta do México com uma cobrança correspondente: Cafe Central, 320 MXN.

“Vi en mi estado de cuenta un cargo de 320 pesos mexicanos de Cafe Central del 12 de junio y no lo reconozco.”Linha es-MX, mostrada em espanhol (AL)
  1. Mascaramento. O código mascara os identificadores pessoais do texto antes de qualquer chamada ao modelo.
  2. Roteador de intenção. O modelo rotula a intenção como uma consulta de cobrança. Não decide mais nada.
  3. Busca de cobranças. O código lê as cobranças da conta da sessão e encontra uma correspondência.
  4. Motor de políticas. O código verifica o prazo da disputa, o status e o valor. A política permite a disputa.
  5. Caixa de confirmação. O cliente confirma a cobrança. O sistema não abre nada antes disso.
  6. Caso aberto. O código abre o caso, o relê e mostra o número do caso.

Resultado. Um caso verificado. O sistema diz que o caso existe só depois de relê-lo.

Caso ambíguo

Uma conta da Colômbia com várias cobranças que poderiam corresponder.

“não reconheço uma cobrança”pt-BR, depois: não reconheço, pode revisar?
  1. Mascaramento. O código mascara os identificadores pessoais do texto.
  2. Roteador de intenção. O modelo rotula a intenção como uma consulta de cobrança.
  3. Busca de cobranças. O código encontra mais de uma cobrança candidata.
  4. Motor de políticas. O texto não nomeia uma única cobrança. O código não adivinha.
  5. Qual cobrança? A página mostra as cobranças candidatas como botões. O cliente escolhe uma.
  6. Nada é aberto. Nenhuma disputa é aberta e nenhum caso existe até que o cliente escolha e confirme.

Resultado. Uma pergunta, não uma ação. Nada é aberto também com a segunda mensagem pouco clara.

É preciso uma pessoa

Uma conta da Argentina. O cliente pede um atendente.

“Quiero hablar con un asesor.”Linha em espanhol. Em pt-BR: quero falar com um atendente
  1. Mascaramento. O código mascara os identificadores pessoais do texto.
  2. Roteador de intenção. O modelo rotula a intenção como um pedido de uma pessoa.
  3. Motor de políticas. O primeiro pedido oferece ajuda. Um segundo pedido registra uma transferência. Quem decide é o código, não o modelo.
  4. Transferência. O código monta o pacote para o atendente com seus próprios registros.
  5. Visão do atendente. O atendente lê o pacote em uma visão somente leitura, com o rastro de cada passo.

Resultado. Uma transferência com os fatos verificados, para que o cliente não repita a história.

O pacote da transferência

Esta é a forma do que o atendente recebe. Não tem identificador de cliente nem transcrição bruta. Os valores vêm da conversa, então esta página mostra só os campos.

request
A intenção que o sistema entendeu. Um código, não as palavras do cliente.
summary
Um resumo fixo da conversa, montado a partir dos turnos.
conversation
Cada turno como códigos e referências. Sem transcrição bruta.
verified_facts
Os fatos da cobrança que o código leu dos dados.
actions_taken
Cada passo que o sistema tentou, com seu turno e seu resultado. Também os passos com falha.
evidence
Referências que sustentam os fatos.
open_questions
O que o atendente ainda precisa perguntar.
language, country, phase
Em que ponto está o caso e em que idioma.
