Tres casos, un mapa de decisión

Los mismos pasos se ejecutan cada vez. El código decide a dónde va el turno. Elige un caso para iluminar su ruta.

Caso normal

Una cuenta de México con un cargo que coincide: Cafe Central, 320 MXN.

“Vi en mi estado de cuenta un cargo de 320 pesos mexicanos de Cafe Central del 12 de junio y no lo reconozco.”Línea es-MX, mostrada en español (LA)
  1. Enmascaramiento. El código enmascara los identificadores personales del texto antes de cualquier llamada al modelo.
  2. Enrutador de intención. El modelo etiqueta la intención como una consulta de cargo. No decide nada más.
  3. Búsqueda de cargos. El código lee los cargos de la cuenta de la sesión y encuentra una coincidencia.
  4. Motor de políticas. El código revisa el plazo de la disputa, el estado y el monto. La política permite la disputa.
  5. Cuadro de confirmación. El cliente confirma el cargo. El sistema no abre nada antes de eso.
  6. Caso abierto. El código abre el caso, lo vuelve a leer y muestra el número de caso.

Resultado. Un caso verificado. El sistema dice que el caso existe solo después de volver a leerlo.

Caso ambiguo

Una cuenta de Colombia con varios cargos que podrían coincidir.

“não reconheço uma cobrança”pt-BR, y después: não reconheço, pode revisar?
  1. Enmascaramiento. El código enmascara los identificadores personales del texto.
  2. Enrutador de intención. El modelo etiqueta la intención como una consulta de cargo.
  3. Búsqueda de cargos. El código encuentra más de un cargo candidato.
  4. Motor de políticas. El texto no nombra un solo cargo. El código no adivina.
  5. ¿Cuál cargo? La página muestra los cargos candidatos como botones. El cliente elige uno.
  6. No se abre nada. No se abre ninguna disputa ni existe ningún caso hasta que el cliente elige y confirma.

Resultado. Una pregunta, no una acción. Tampoco se abre nada con el segundo mensaje poco claro.

Se necesita una persona

Una cuenta de Argentina. El cliente pide un asesor.

“Quiero hablar con un asesor.”Línea en español. En pt-BR: quero falar com um atendente
  1. Enmascaramiento. El código enmascara los identificadores personales del texto.
  2. Enrutador de intención. El modelo etiqueta la intención como una solicitud de una persona.
  3. Motor de políticas. La primera solicitud ofrece ayuda. Una segunda solicitud registra un traspaso. Decide el código, no el modelo.
  4. Traspaso. El código arma el paquete para el asesor con sus propios registros.
  5. Vista del asesor. El asesor lee el paquete en una vista de solo lectura, con la traza de cada paso.

Resultado. Un traspaso con los datos verificados, para que el cliente no repita la historia.

El paquete del traspaso

Esta es la forma de lo que recibe el asesor. No tiene identificador de cliente ni transcripción en bruto. Los valores salen de la conversación, así que esta página muestra solo los campos.

request
La intención que entendió el sistema. Un código, no las palabras del cliente.
summary
Un resumen fijo de la conversación, armado con los turnos.
conversation
Cada turno como códigos y referencias. Sin transcripción en bruto.
verified_facts
Los datos del cargo que el código leyó de los datos.
actions_taken
Cada paso que el sistema intentó, con su turno y su resultado. También los pasos fallidos.
evidence
Referencias que respaldan los datos.
open_questions
Lo que el asesor aún necesita preguntar.
language, country, phase
Dónde está el caso y en qué idioma.

Fuente: HandoffPackage y el mock del asesor.
